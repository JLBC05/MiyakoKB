# MiyakoKB 深度审计决策记录

## 项目识别

- **结论**：本次审计对象为 `Saber-Translator-main` 目录中的 MiyakoKB（版本 `0.1.0`，存储版本 `3.5.4`），而非已经移除翻译能力的上游 Saber-Translator。
- **理由**：项目 README 明确说明该派生项目已改写为漫画知识库，并与上游在功能、数据库结构和接口上不兼容；审计必须以当前代码为准。

## 工作方式

- **结论**：采用「4 · 深挖」强度，检查目标、边界情况、风险、遗漏和默认假设。
- **理由**：用户明确选择该强度。
- **结论**：保留决策记录；本轮先审计并制定优化与演进方案，不直接修改业务代码或实施优化。
- **理由**：用户明确要求保留记录；项目约束要求方案经确认后再实施。
- **结论**：审计证据区分「已验证缺陷」「静态高风险隐患」「待复现假设」「优化建议」，避免把猜测当作 Bug。
- **理由**：深度审计需要可追溯的文件/行号、触发条件、影响与验证证据。

## 已确认的项目背景

- 默认单用户、本地优先，但支持邀请码注册、多用户配额和公网部署。
- Windows/Python 3.11+/Node 22+；Flask + Waitress API、独立 Worker、SQLite、对象存储和 ChromaDB。
- 关键业务链路：漫画导入 → 多模态逐页分析 → 实体对齐 → 分层聚合 → 向量检索问答/角色与世界书蒸馏。
- 已有后端 pytest、前端 Vitest/typecheck/lint/UI 审计/OpenAPI 契约门禁；测试结果仍需实测，不能据文档推断全绿。

## 审计范围与演进决策

- **结论**：本地单用户部署优先，公网多用户安全只作次级检查。
- **理由**：用户明确选择；审计资源优先投入本地数据与核心链路，不将公网上线作为当前验收目标。
- **结论**：允许离线测试和本地复现，禁止真实模型/API 调用；允许只读使用现有本地漫画、SQLite 和 ChromaDB 样本。
- **理由**：用户明确授权；原数据保持只读，动态复现使用隔离的临时库和测试产物，避免污染真实知识库。
- **结论**：演进目标优先级为 `正确性与数据安全 → 知识质量 → 性能与资源效率 → 产品能力扩展`。
- **理由**：用户明确确认该顺序；性能不得绕过一致性，新功能不得优先于可信的数据和引用链路。
- **结论**：保持现有 SQLite 数据及对象资产的可迁移性、Windows 单机启动、OpenAI 兼容模型接入，不引入必须常驻的新基础设施；已有任务、分析结果和向量索引尽量复用。
- **理由**：用户要求保持兼容；确有重建必要时，方案必须说明迁移、回退及重建成本。
- **结论**：用户当前没有已观察到的特定故障；审计从高风险不变量和端到端数据流主动寻找问题，而非围绕既有症状排查。
- **理由**：用户回复“无”。
- **结论**：演进方案按版本迭代组织：止血修复 → 近期稳定性 → 中期质量/性能 → 长期新功能；各项附依赖和验收标准，不作无依据的固定工期承诺。
- **理由**：用户选择版本迭代方式。
